# 2026-10-16 跌倒检测修复记录

当前算法版本：`2026-10-16-observed-v4`。本文件记录本轮实际生产上传任务处理器的回归结果；以前版本的结果不能替代本轮验证。

## 原因

- 人体框存在不等于骨架可靠。录屏小人物、运动模糊、正面倒地会让 YOLOv8n-Pose 丢掉肩髋或给出错误直立姿态，导致连续候选中断。
- 录屏黑边占用输入像素。自动裁剪后直接运行时序模型又会改变归一化坐标、人体宽高比和位移分布，本轮对照没有稳定收益，最终移除自动裁剪。
- 瞬时运动信号不适合直接连续保持 0.5 秒；沿用真实倒地变化加持续低位姿态、TCN 支持的判定。真正姿态缺失仍断开计时。
- 旧分析重置整条管线可能清掉已确认事件及跌倒前历史。本轮处理器对每帧只推进一次，补检在跟踪和分类之前完成，完成事件留存。
- TCN 权重实际是 large 架构。配置统一为 large，继续严格加载权重；检测错误明确报错，应用不使用模拟姿态替代真实识别。

## 最终修改

上传：YOLO11m-Pose，1280×736，逐帧检测；疑难人体局部放大与旋转补检后还原全画面坐标。保留原 `checkpoints/best.pth`，不重训、不降低 0.3 模型支持阈值，不按文件名或测试标签触发报警。关键点完整度门控为 0.35，肩髋有效性另有检查。

摄像头：保持 YOLOv8n-Pose、512×288、逐帧检测与既有曝光、亮度、预览设置。本轮主要验证离线上传，不能将离线测试结果当成摄像头帧率测试。

报警：连续约 0.5 秒疑似状态，人工解除或 30 秒保持。文件按视频时间判断，摄像头按实际时间。短暂姿态抖动容忍仍为原 .12 秒，缺失不会用旧骨架填补。

显示：每人的 ALARM 标签只取该人的报警状态，避免一人报警导致旁人也显示 ALARM。诊断额外记录核心关节是否有效和逐帧关键点。

较大姿态模型约 2091 万参数，超出原比赛 2000 万参数限制；当前选择服务于用户的本机项目演示，不能据此宣称满足原赛题约束。姿态权重约 40.5 MiB，需 Ultralytics >=8.3.0。

## 回归方式与证据

- `scripts/regress_video_jobs.py` 直接运行与网页相同的 `VideoAnalysisJobs._run`，真实解码、检测、跟踪、分类、报警、编码，逐个生成报告及回放。未用历史检测缓存。
- 正样本目录：本机授权的测试视频目录（默认可放在项目根目录的 `test/`，该目录被 Git 忽略），22 个视频。回归产物保存在本机 `app_data/` 下，不应提交到公开仓库。
- 负样本：`test_neg`，23 个行走及 2 个全程躺卧，共25个。回归产物 `app_data/regression_final_negative/summary.json`。
- 标签只参与结果核对，不进入推理。`manifest.json` 保存模型、配置哈希及运行库版本。
- 每个正样本抽取报警前约 .65 秒、.25 秒和触发时刻，核对人体、骨架和倒地过程，图片保存在 `app_data/verification`。不是人工逐帧完整观看全视频。
- 另通过网页选择并上传滑板视频，确认 Spring Boot 转发、检测结果和回放；任务 `2c0485d647134db9967f8f54c6d316ac`，1 个事件，4.700 秒触发，处理 96.40 秒；诊断在 `app_data/verification/web_report.json`。

## 使用与边界

新服务已经启动，网页旧记录不会自动改写；重新上传才会重新分析。隔离回归不清除用户历史、不写入实时摄像头的 MySQL 统计。

测试素材参与排查，不是独立测试集。仍需补充坐下、深蹲、捡物、主动躺下、多人与长时间无人场景；不能声称未知视频均无漏报误报。正常视频最高模型分数较高，模型分数不能解释为准确率。骨架仍可能在遮挡和家具处误识别，不能宣称逐帧姿态完全正确。

`20.54.05.17.mp4` 包含同一动作的两个摄像机视角。系统按画面中不同人物轨迹分别记录，可能有两条事件，不能直接解释为两次独立事故。

复现：在项目目录运行 `python scripts/regress_video_jobs.py --source test --output app_data/recheck_positive`；负样本使用 `--source test_neg --negative --output app_data/recheck_negative`。请仅使用你有权处理的本地素材；脚本在空测试集或标签判断不符时返回失败退出码。
