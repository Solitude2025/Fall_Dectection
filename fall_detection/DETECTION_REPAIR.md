# 跌倒漏检、误报修复与验证（2026-10-15）

本次目标是修复用户提供的 Desktop 视频漏报，并检查原有视频与正常行为是否出现退化。应用沿用 `yolov8n-pose.pt` 和 `checkpoints/best.pth`，没有重新训练、替换权重或降低原 TCN 支持阈值。已执行代码修复、离线回归、Spring Boot 上传链路复测及网页报告/回放检查。

人工视觉核对包括原视频抽帧、跌倒区间的骨架关键帧、网页报告和回放画面；不声称人工逐帧完整观看全部视频。算法推理处理了上传视频的所有帧，YOLO 仍按配置隔帧执行。

## 一、原因与证据

### 1. 第一个视频：跌倒时姿态丢失

`Desktop 2026.10.15 - 14.25.43.08.mp4` 是录屏素材。小人物、黑边和运动模糊使原检测器在失衡、倒地时多次丢失人体姿态。没有可靠骨架，后面的时序分类器就缺少动作依据。旧跟踪逻辑还曾把历史骨架重复当成新观测，这会掩盖真正的姿态缺失。

### 2. 第二个视频：有框不等于骨架正确，也不等于满足报警规则

`Desktop 2026.10.15 - 14.28.46.09.mp4` 中人体朝摄像头方向倒下。二维躯干角度的变化可能小于侧向跌倒；在倒地关键帧中还看到腿部关键点落向错误位置、把横躺的人解释成近似直立的骨架。框仍然存在，不能证明肩、髋、腿都标注正确。

原在线规则偏重瞬时速度、躯干角度、框变化；这些短时信号再经过连续 0.5 秒要求，容易在跌倒后静止时中断，导致不报警。人体框骤缩还可能更换跟踪编号，使动作序列从头积累。

### 3. “训练集主要是左右侧摔”的猜想尚未证实

按 `data/raw/omnifall/of-syn.csv` 中 `label=1` 的视频路径去重统计，`camera_azimuth` 为 front 549、left 532、rear 528、right 527。它们是摄像机方位标签，不等价于人物在画面中的运动方向；只能说明源数据的摄像机方位没有明显偏向左右。

本机处理后的训练/验证/测试样本分别为 2048/256/256，每个关键点序列为 81 帧，但数字文件名缺少视频来源和帧率信息。因此不能确认当前权重实际训练子集的方向比例，也不能直接推断训练采样帧率。正面跌倒泛化不足依然可能存在，需要恢复样本映射后验证。

### 4. 误报：模型容易把“处于躺卧姿态”当成“发生跌倒”

本机两个全程躺卧的负样本，原策略均触发报警。这说明只看某一时刻的低位、横躺姿态和模型高分，不足以区分跌倒与正常躺卧。普通行走中也有较高 TCN 分数，所以页面百分比不能直接当作识别准确率。

## 二、已实施修复

1. **真实图像的姿态重识别**：新增 `pipeline/pose_recovery.py`。对已有轨迹的疑难区域局部放大、旋转 90/270 度推理，再把坐标还原。结合关键点完整度、检测分数和历史躯干尺度选择结果；必要时增加局部 960×960 推理。每检测帧最多两个区域、每区域最多六次额外检测，丢失超过 0.6 秒放弃旧区域。不把姿态缺失直接当作跌倒。
2. **观察动作变化再判断持续姿态**：新增 `pipeline/fall_transition.py`。依据肩部下降、人体高度压缩和躯干转动建立短期变化证据，随后要求低位/倾斜状态与 TCN 分数共同支持。度量使用像素坐标，避免画面宽高比扭曲躯干角度，不要求人物必须向左或向右移动。
   对远距离小人物增加一次最多约 0.12 秒的姿态抖动容忍，但要求此前已经连续观察到约 0.35 秒的低位候选；真正的姿态缺失仍然硬重置 0.5 秒计时。
3. **保持轨迹，拒绝虚构连续性**：框重叠不足时，使用多个可见关节的位移辅助关联同一人物。真正漏检时停止喂入旧骨架，清空 TCN 序列并重置 0.5 秒计时；只保留短期真实观测供变化判断参考。肩、髋长期缺失不能延长旧变化证据。
4. **报警语义保持**：疑似信号连续约 0.5 秒才创建事件，保持 30 秒或人工解除。上传按视频帧数计时；摄像头按真实经过时间判断，避免额外推理变慢导致时长失真。摄像头超时在后续帧处理中检查，仍受处理延迟影响。
5. **页面与诊断可解释**：页面改称“模型分数”，提示其不等于准确率；保留姿态缺失提示。报告新增 `analysis_version`、`decision_policy`、`processing_seconds`，逐帧诊断保存变化理由、肩部下降比例、姿态高度比和模型支持结果。旧报告保留原结论，不追溯改写。

应用配置已启用 `pipeline.pose_recovery=true`、`pipeline.require_observed_transition=true`。两者的构造参数默认值保留为 false，兼容旧评测调用；复现实验时必须明确使用哪一种策略。

### 新增远距离视频：`Desktop 2026.10.15 - 18.58.49.11.mp4`

首次复测时，人物位于竖屏画面中央且占比很小。倒地区间仍能得到人体框和模型分数，最高约 0.829，但倒地变化后的候选最长只有 0.467 秒，未达到 0.5 秒；逐帧诊断显示中间有一次小目标骨架异常，候选被清零。这解释了“有框却不报警”：框存在不代表每一帧的关键点都稳定，也不代表产品连续计时已经完成。

已在 `FallTransition` 增加有界抖动容忍：只有已经持续约 0.35 秒的低位候选，才允许跨过一次不超过约 0.12 秒的姿态异常；这段容忍不会更新最后一次有效候选时间，因此人物恢复站立后不会无限延长候选。真正的姿态缺失仍由管线清空时序并让 `AlarmStateManager` 重置 0.5 秒计时。

该视频离线复测触发时间约 6.215 秒；随后用当前运行的 Python + Spring Boot 网页上传链路再次复测，任务 `f262630843884778a8b8278744364dd1` 产生 1 个事件：候选开始 5.731 秒、触发 6.215 秒，最高模型分数 0.829，视频 7.747 秒，处理约 67.69 秒。报告在 `app_data/video_jobs/f262630843884778a8b8278744364dd1/report.json`。有效人体姿态比例约 48.82%，这是整段视频的比例，前面包含无人或难以识别的远景片段。

这次改动不是把所有远处框都视为跌倒，也没有把 0.5 秒产品规则改短。它只处理已经出现明确倒地变化后的短暂骨架抖动。25 个负样本回归仍为 0 个报警（23 个行走、2 个全程躺卧），19 项自动测试通过。

## 六、后续修复路线与当前边界

当前工程修复解决了用户指定的两个漏报，但没有根治模型泛化问题。后续应先补数据和评估，再训练：

1. 保存原视频来源、摄像头角度、人物编号、帧率和跌倒起止时间；核对训练与推理的时间采样。按人物/场景划分训练验证测试集，避免同一源视频泄漏。
2. 增加朝向/背向摄像头跌倒，以及坐下、深蹲、躺下、捡东西、遮挡和小人物样本；使用独立验证集选择模型阈值与姿态恢复开销。
3. 用事件召回、每小时误报数、重复报警、报警延迟和实际处理帧率评估。移动镜头需单独验证，当前推荐固定摄像头。
4. 在数据和算力允许后微调姿态/时序模型。单纯左右翻转不能把侧向跌倒变成真实正面跌倒，不应当作补齐视角数据的办法。
5. 局部旋转恢复增加 CPU 成本，本机第一段约 5.93 秒素材用了约 33 秒分析，目前不能承诺摄像头满帧实时。应以实际实时帧率测量为准，再评估 GPU/ONNX 或减少恢复频率，并重新检查准确性。

为了减少全程躺卧误报，新策略要求观察到变化；代价是开头已倒地、跌倒过程在镜头外或长时间遮挡的视频可能不报警。普通单目骨架也可能无法可靠区分主动快速躺下与跌倒。这些情况需要新数据与策略评估，不能靠继续下调阈值解决。

### 摄像头实时性能修复（2026-10-15）

摄像头与上传视频现在使用不同的运行配置：上传视频保留 `pose_recovery=true` 和原检测分辨率；摄像头关闭额外姿态恢复，使用较小输入、每 3 帧检测一次，并在有 NVIDIA GPU 时使用 CUDA。采集线程只保留最新帧，推理来不及时丢弃过期帧，避免画面延迟不断累积。摄像头还会请求 DirectShow 的 MJPEG、640×480、30 FPS 和自动曝光参数。页面显示采集 FPS、输出 FPS 和丢弃帧数，便于区分设备采集瓶颈与模型推理瓶颈。

在本机 RTX 4060 和 `USB2.0 HD UVC WebCam` 上实测：采集约 29.9 FPS，标注输出约 25.8 FPS，单帧推理约 5～18 ms。摄像头驱动在 OpenCV 默认曝光下曾只有约 7～8 FPS；新的 MJPEG/自动曝光设置恢复了采集帧率。没有 CUDA 时服务会自动回退 CPU，此时输出速度会取决于机器算力。
