# 跌倒检测应用版说明

这次升级保留原来的 Python 模型，支持上传视频分析和设备实时监测两种模式。Python 负责识别，Spring Boot 负责网页接口、视频转发和实时事件入库，浏览器负责回放、报警和统计图表。

## 两种模式

- **设备实时监测**：当前连接笔记本摄像头，点击启动后显示实时检测画面。报警保存在 MySQL 中，页面支持视觉、声音提醒和人工解除，提供近 7 天统计。
- **上传视频分析**：选择 MP4、AVI、MOV、MKV、WebM 文件，上传后异步分析，显示进度、疑似跌倒次数和可跳转到事件时间点的 H.264 MP4 回放。限制为 100 MiB（页面标为 100 MB）、5 分钟、1080p。

第一版一次只运行一种分析。切换页面不会擅自停止正在运行的摄像头；上传前请先点击“停止摄像头”。视频分析运行中也不能启动摄像头。

上传区支持“单视频分析”和“批量导入检测”。批量模式可多选视频，或将多个视频拖入回放窗口，按顺序逐条上传和检测；每个文件仍受 100 MiB、5 分钟、1080p 限制。导入后点击开始，可继续添加文件、移除待检测项，或选择“本条完成后暂停”，每条完成后均可查看结果和回放。无效格式、空文件、超大文件在导入时提示；分析失败不影响下一条，网络中断或服务冲突则暂停队列，避免不确定状态下重复上传。查看历史结果或切换设备页面不会中断队列。

回放窗口支持“将视频拖到此处”，拖入多个文件会自动进入批量模式；拖入仅加入待检测列表，不会立即上传。无论是否已有回放，都可以继续拖入。批量待上传文件只保留在当前浏览器页面，需保持页面打开；关闭或刷新会丢失未上传队列，已上传的分析结果仍保存在本机历史中。

视频报告和压缩回放保存在项目 `app_data/video_jobs/<job_id>/`，重启 Python 后可从“最近视频分析”打开。原始上传文件和编码中间文件在处理结束后删除。当前报告列表显示最近 20 条，磁盘结果不会自动删除，请按需要清理旧任务文件夹。

摄像头状态中的“采集 FPS”表示设备实际送来的帧率，“输出 FPS”表示网页收到的标注帧率；“丢弃帧”是推理来不及时主动跳过的旧帧，避免画面越积越延迟。实时模式会优先使用 GPU、MJPEG 和较小输入尺寸，并只保留最新帧。默认使用自动曝光（`camera_auto_exposure: 0.75`），`camera_exposure: null`。暗处允许摄像头降低真实采集帧率以获得足够曝光，不再强制 `-5` 短曝光来维持 30 FPS。本机对比中固定 `-5` 的原始亮度约 19/255，自动曝光约 107/255、15 FPS；数值随现场光线变化。

预览只做有上限的轻微提亮并保留黑位，避免把欠曝光噪声整体抬成灰雾；检测输入继续使用现有低光预处理。状态接口新增 `raw_brightness`、`preview_brightness`、`preview_gamma`，便于区分采集欠曝与显示问题。部分 DirectShow 驱动的曝光读回为 `-1`，因此另记 `camera_exposure_mode_requested` 和 `camera_auto_exposure_accepted`，不把不支持的读回当成自动曝光实际状态。仍暗时先检查镜头遮挡、照明与其他相机程序占用。只有明确需要手动曝光时才设置 `camera_auto_exposure: 0.25` 和 `camera_exposure`，配置修改后重新启动摄像头。

视频分析中的时间按原视频帧率计算，不受模型处理速度影响。`video_time_seconds` 表示疑似行为在原视频中的开始秒数，`trigger_time_seconds` 表示达到 0.5 秒触发时的秒数。回放中的报警显示按视频时间保持 30 秒；短视频可能在解除前结束，报告里的 `active` 只描述视频最后一帧状态，不是当前现场报警。上传结果单独保留，不发送实时声音提醒，也不混入设备的 MySQL 报警统计。

“未触发报警”只表示本次算法没有满足报警条件。若人体出现后连续至少 0.25 秒没有可靠姿态，报告会显示需要人工复核及缺失时间段；这项质量提示不改变 `has_fall`，也不会额外触发报警。报告新增 `quality` 和 `timeline`，记录有效人体帧比例、姿态缺失时长、TCN 分数、规则候选和最终报警，便于定位漏检。没有人体的背景片段不等于识别故障；该提示也不能判断缺失区间内是否真的跌倒。

检测器漏检时，跟踪器保留编号用于重新关联，但不再把旧骨架作为当前姿态送入时序模型。缺失后重建时序缓冲，防止跨越未观察片段拼接动作。录屏包含浏览器边框、黑边、重复帧及较小人体，可能降低识别效果；建议使用原始视频。

## 2026-10-16 上传视频检测更新

上传视频现在使用 `yolo11m-pose.pt`（1280×736 输入）逐帧检测，并在疑难姿态区域做真实图像的局部旋转补检。原 `checkpoints/best.pth` 跌倒时序分类权重保持不变。摄像头继续使用原 `yolov8n-pose.pt` 和原实时输入、曝光及预览设置。

本轮对照中，自动裁掉录屏黑边会改变时序分类的归一化位置与尺度特征，结果反而变差，因此上传分析保持完整画面；局部补检会先还原到完整画面坐标再跟踪、分类。真正缺失的姿态仍会断开连续报警计时。

较大姿态模型的分析速度较慢；网页显示的是原视频帧率，处理时间可以超过视频时长。首次部署会由 Ultralytics 下载约 40.5 MiB 的姿态权重。YOLO11m-Pose 约 2091 万参数，超过原比赛 2000 万限制，因此当前配置面向求职演示的本机离线分析；若仍需参加原赛题，应另用小模型配置并单独验证。

重启 Python 服务后重新上传才能使用新算法。旧历史结果保持原来的分析版本和结论，不会自动改写。

## 2026-10-15 漏检修复

应用默认启用了两个配置，位于 `configs/config.yaml` 的 `pipeline` 下：

- `pose_recovery: true`：对已跟踪的人物，在低分、丢失或近期倾斜时执行局部放大、旋转重识别；低质量时增加局部高分辨率检测。结果必须来自真实图像，不补造缺失骨架。每个检测帧最多处理两个区域，每区域最多增加六次检测。
- `require_observed_transition: true`：先观察到肩部下降、人体高度压缩或躯干转动等变化，再结合持续低位姿态和原 TCN 模型分数判断；不再要求瞬时速度峰连续保持 0.5 秒。仅全程躺卧不作为发生跌倒的证据。

远距离小人物可能出现单帧骨架抖动。已经持续观察到低位候选约 0.35 秒后，系统最多容忍约 0.12 秒的一次姿态异常；真正的姿态缺失仍会重置报警计时。

这次没有重新训练或替换权重，也没有降低原 TCN 支持阈值。网页将“置信度”改称“模型分数”；分数没有经过概率校准，不能解释成正确率。产品输出仍是是否报警。

疑似状态需要连续 0.5 秒，姿态缺失会重新计时。视频文件按媒体帧时间计算；摄像头按真实经过时间计算 0.5 秒和 30 秒，避免推理变慢后用标称帧率错误延长计时。报警在后续帧处理中检查超时，检测卡顿仍会带来提醒延迟。

用户提供的四个测试视频在 Spring Boot 上传链路复测均生成一个事件，前三个触发时间分别为 4.750 秒、5.317 秒和 0.875 秒；新增远距离视频 `Desktop 2026.10.15 - 18.58.49.11.mp4` 在 6.215 秒触发。第二个视频结尾仍有 0.5 秒姿态缺失提示。旧分析结果保留原判定，要查看新版结果请重新上传，或打开“最近视频分析”中本次生成的报告。新报告带有 `analysis_version`、`decision_policy` 和 `processing_seconds`，完整诊断保存在任务目录的 `report.json` 中。

局部重识别增加 CPU 开销：本机这三段视频处理耗时约 33 秒、12 秒、5 秒，视频时长约 5.93 秒、6.23 秒、5.06 秒；这是离线上传的耗时，不能当作摄像头实时帧率保证。当前适合先验证检测效果，实时性能仍需单独测量和优化。可将 `pose_recovery` 设为 `false` 比较速度，但姿态恢复能力也会下降；配置修改需要重启 Python 服务。

已知限制：开头就已经倒地的视频可能不报警；移动镜头仍有漏检；深蹲、快速坐下和主动躺下等困难负样本不足，不能保证不误报。现有小规模回归不代表实际养老场景准确率。后续应保留独立测试集，补充不同方向跌倒与上述负样本，核查帧率和训练子集来源后再训练。完整原因、修复与回归得失见 [DETECTION_REPAIR.md](DETECTION_REPAIR.md)。

## 当前范围

当前只输出一个产品结论：`alarm = true` 或 `alarm = false`。

- 连续疑似跌倒达到 0.5 秒，才创建报警事件；
- 报警创建后保持 30 秒；
- 也可以在网页中人工解除；
- 解除后必须先出现一帧正常状态，才允许下一次跌倒重新触发，避免同一个人躺着不动时反复报警；
- 当前摄像头固定为本机摄像头 `camera_id=laptop_camera`；
- 当前没有登录用户和多设备管理。网页上的“操作员”就是运行本程序的人，后续增加外置摄像头时再把摄像头表和配置页面加入。

## 三个进程分别做什么

```text
浏览器（Spring Boot 提供页面）
          │ REST 请求
          ▼
Spring Boot :8080 ───── MySQL
          │ 调用本机 Python 服务
          ▼
Python 推理服务 :8001 ───── 笔记本摄像头
          │
          └── YOLO Pose → ByteTrack → Light-TCN → 报警状态机
```

Spring Boot 不重新实现 PyTorch 模型。它保存事件、提供网页接口、转发启动/停止摄像头的命令。这样每一层的职责比较清楚，也便于以后把 Python 模型换成 ONNX 或部署到边缘设备。

## 事件 JSON 字段

Python 创建报警时会向 `POST /api/internal/events` 发送下面这类记录：

```json
{
  "event_id": "evt_20261014T102011123456Z_a1b2c3d4",
  "camera_id": "laptop_camera",
  "person_id": 3,
  "event_type": "fall_suspected",
  "confidence": 0.91,
  "start_time": "2026-10-14T10:20:11.123456Z",
  "alarm_level": "high",
  "status": "active",
  "start_frame": 120,
  "trigger_frame": 135,
  "end_frame": 135,
  "duration_frames": 16,
  "duration_seconds": 0.533,
  "cleared_at": null,
  "clear_reason": null,
  "expires_at": "2026-10-14T10:20:41.123456Z",
  "created_at": "2026-10-14T10:20:11.623456Z"
}
```

| 字段 | 含义 |
|---|---|
| `event_id` | 这一次报警的唯一编号。前端人工解除时用它定位事件。 |
| `camera_id` | 产生事件的摄像头。现在固定为 `laptop_camera`，以后可以换成 `room_01` 等编号。 |
| `person_id` | ByteTrack 给画面中人体分配的临时编号。它不是用户身份，也不是老人档案编号。 |
| `event_type` | 事件类型。当前只有 `fall_suspected`，表示“疑似跌倒”。 |
| `confidence` | 触发报警时的模型分数，范围通常为 0 到 1。新版使用 TCN 平滑分数；它没有经过概率校准，不等于准确率。字段名保留以兼容后端。 |
| `start_time` | 连续疑似跌倒行为开始的时间。 |
| `alarm_level` | 报警等级。当前统一为 `high`，以后可以增加低、中、高。 |
| `status` | 事件状态：`active` 表示待处理，`cleared` 表示已经解除。 |
| `start_frame` | 连续疑似跌倒信号开始的帧号。用于回看和调试。 |
| `trigger_frame` | 达到 0.5 秒并正式触发报警的帧号。 |
| `end_frame` | 当前已经记录到的最后一帧。自动解除或人工解除时会更新。 |
| `duration_frames` | 从行为开始到最后记录帧的帧数。 |
| `duration_seconds` | `duration_frames / fps`，表示累计视频帧时长。摄像头掉帧或推理变慢时它不等于真实经过时间，真实时间应比较时间字段；报警计时不依赖此值。 |
| `cleared_at` | 解除时间。报警仍然 active 时为 `null`。 |
| `clear_reason` | 解除原因：`manual` 表示人工解除，`timeout_30s` 表示 30 秒自动解除。 |
| `expires_at` | 按当前规则预计自动解除的时间。前端可以用它显示倒计时。 |
| `created_at` | 报警事件写入系统的时间。它可能比 `start_time` 晚约 0.5 秒。 |

`timestamp` 和 `max_probability` 还会出现在 Python 离线结果中，用来兼容原来的评测脚本；Spring Boot 的数据库接口不依赖这两个兼容字段。

## 启动方式

### 第一次准备

需要安装：

1. JDK 17；
2. Maven；
3. MySQL 8，或者 Docker Desktop；
4. Python 项目原有依赖，以及新增的 FastAPI、Uvicorn、Requests。

如果使用 Docker，项目根目录已经提供 MySQL 配置：

```powershell
docker compose up -d mysql
```

如果暂时没有 MySQL，可以先使用 H2 练习：启动 Spring Boot 前设置：

```powershell
$env:SPRING_PROFILES_ACTIVE = "h2"
```

### 启动 Python 推理服务

在项目根目录运行：

```powershell
python -m services.inference_service --camera-index 0
```

`--camera-index 0` 表示电脑的第一个摄像头。启动后，Python 服务地址是 `http://127.0.0.1:8001`。
默认只启动服务，摄像头由页面按钮开启，方便直接选择上传视频模式。需要开机立即监测时可加 `--auto-start`。服务根据权重形状识别模型架构；缺少权重或模型加载失败会报错，不会用随机权重或模拟人体代替真实检测。

### 启动 Spring Boot

在另一个终端运行：

```powershell
cd backend
mvn spring-boot:run
```

后端地址是 `http://localhost:8080`，浏览器打开这个地址即可看到监控台。

也可以直接运行项目根目录的 `start_inference.ps1` 和 `start_backend.ps1`。

电脑重启后，可以在项目根目录直接双击 `start.bat` 一键启动 Python 推理服务和 Spring Boot。脚本会先尝试使用已经运行的 MySQL；如果 Docker Desktop 已经启动，还会自动启动项目的 MySQL 容器并等待端口可连接；如果 MySQL 暂时不可用，则自动使用文件型 H2。H2 与 MySQL 的事件记录相互独立，不会自动迁移。MySQL 端口可连接但账号或数据库配置不正确时，仍需查看后端日志处理连接错误。

启动器确认两个服务的健康接口均正常后，会自动打开 `http://localhost:8080`；CMD 窗口会一直保留，使用网站时请保持它打开。关闭这个窗口、按 Ctrl+C 或运行 `stop.bat`，都会停止本次启动的 Python、Java 和所有子进程。启动失败也会清理已经启动的服务并保留错误提示。详细输出保存在 `app_data/logs/` 下的 `inference.stdout.log`、`inference.stderr.log`、`backend.stdout.log`、`backend.stderr.log`，下次启动该服务时会覆盖对应日志。项目若有 `.venv` 或 `venv`，优先使用其中的 Python，否则使用系统 Python。默认最多等待服务启动 120 秒。

同一项目只允许一个启动窗口，重复双击会提示已有运行窗口。端口被其他程序或旧版后台服务占用时会提示冲突；应先停止原服务。`stop.bat` 只通知本项目的启动窗口退出，不再按端口结束其他程序。摄像头仍由网页中的按钮开启。终端验证时可运行 `start.bat -NoBrowser`，启动并保持服务但不打开网页。已有视频报告与数据库文件保留；关闭窗口会中断尚未完成的分析。外部 MySQL 或 Docker 数据库保持原有运行状态。

## 主要接口

- `GET /api/health`：检查 Spring Boot 是否正常；
- `GET /api/camera/status`：查看笔记本摄像头和 Python 推理服务状态；
- `POST /api/camera/start`：启动摄像头；
- `POST /api/camera/stop`：停止摄像头；
- `GET /api/events?limit=50`：查询最近事件；
- `POST /api/events/{eventId}/clear?reason=manual`：人工解除报警；
- `GET /api/events/stats?days=7`：查询统计数字和按日趋势；
- `GET /api/camera/stream-url`：取得前端播放的本机 MJPEG 地址。
- `POST /api/videos`：上传视频（multipart 字段名为 `file`），返回分析任务编号；
- `GET /api/videos`：最近 20 个视频任务；
- `GET /api/videos/{jobId}`：进度、结果和事件时间点；
- `GET /api/videos/{jobId}/result`：MP4 回放，支持 Range 请求以拖动进度。

## 这一版之后的自然扩展

先把当前链路跑通，再考虑外置摄像头、报警器、登录用户和姿势分析。加外置摄像头时，最先需要新增的是 `cameras` 表和摄像头选择页面；这不影响当前 `fall_events` 表和报警接口。
